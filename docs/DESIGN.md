# NewsServer 설계

뉴스·공시를 **한 번만 수집**해 저장하고 HTTP로 제공하는 로컬 서버다. 여러 애플리케이션이
같은 피드를 각자 폴링·파싱·저장하는 대신 이 서버 하나를 조회한다.

- 형태: FastAPI + SQLite(WAL, FTS5) 단일 프로세스
- 기본 주소: `http://127.0.0.1:5200`
- API 상세: [API.md](API.md)

---

## 1. 목표와 비목표

**목표**
- 소스(피드·API)당 한 번만 수집하고, 결과를 모든 클라이언트가 공유한다.
- 종목·주제·카테고리·시장·전문 검색·증분 커서로 조회한다.
- 소스 추가는 설정 파일 한 줄(RSS 기준), 새 종류의 소스는 수집기 클래스 하나로 끝난다.
- 시각은 전부 UTC로 저장하고, 소스별 타임존 문제는 수집 단계 한 곳에서 해결한다.
- 수집 실패를 "새 기사 없음"과 구분해 드러낸다.

**비목표**
- 기사 본문 크롤링 (RSS·API가 주는 요약까지만 저장)
- LLM 요약·감성 분석 (목적이 클라이언트마다 달라 클라이언트에 둔다)
- 외부 공개·다중 사용자 인증 (로컬 전용, 쓰기 요청만 선택적 토큰)

## 2. 구성

```
                 ┌──────────────────────── NewsServer (uvicorn) ─────────────────────────┐
 RSS / 공시 API  │ Scheduler ─► Collector ─► Ingestor (정규화 → 중복 제거 → 태깅)        │
 종목별 검색     │  소스별 next_poll_at       rss / rss_search / dart / edgar / yahoo      │
                 │  시장 시간·백오프·조건부 GET                    │ 단일 writer          │
                 │                                         ┌───────▼────────┐             │
                 │                                         │ SQLite (WAL)   │             │
                 │                                         │  + FTS5 trigram│             │
                 │  FastAPI /v1 ─► QueryService ───────────┴── 읽기 풀 ─────┘             │
                 └──────────────────────────────▲─────────────────────────────────────────┘
                                                │ HTTP (newsclient: fail-soft)
                                          클라이언트 애플리케이션
```

| 모듈 | 역할 |
|---|---|
| `sources.py` | `config/sources.yaml` 로더·검증 |
| `collectors/` | 원격에서 항목을 가져와 `RawItem` 으로 변환 (수집기별 한 파일) |
| `pipeline.py` | 정규화·중복 제거·태깅·저장 (`Ingestor`), 재태깅 |
| `symbols.py` | 심볼 사전(코드↔회사명·별칭), 수집 시점 사전 태깅, 원격 사전 갱신 |
| `topics.py` | `config/topics.yaml` 키워드 규칙으로 주제 태깅, 이름→주제 추론 |
| `matching.py` | 조회 시점 종목 텍스트 매칭 규칙 |
| `query.py` | 헤드라인 조회·주제 통계 |
| `scheduler.py` | 폴링 스케줄, 종목별 수집, 유지보수(보관 정리·백업·사전 갱신), 상태 감시 |
| `storage/` | SQLite 커넥션(단일 writer + 읽기 풀), 스키마 마이그레이션 |
| `api/` | HTTP 엔드포인트 |
| `web/index.html` | 운영 콘솔 — 빌드 없는 단일 페이지, `GET /` |
| `client/newsclient` | 클라이언트용 파이썬 패키지 |

### 2.1 구성 선택

- **SQLite 단일 파일**: 하루 수천 건 규모에서 충분하고(§8 실측), 백업·이식이 파일 하나로 끝난다.
  쓰기는 커넥션 하나를 락으로 직렬화하고 읽기는 읽기 전용 커넥션 풀을 쓴다. WAL 모드라 읽기가 쓰기를 막지 않는다.
- **수집기와 API를 한 프로세스에**: 운영 대상이 하나로 줄어든다. 수집기 예외는 소스 단위 태스크 안에 가두고,
  스케줄러가 멈추면 `/health` 가 `degraded` 를 보고한다.
- **푸시 대신 커서 폴링**: `since_id` 커서로 "새 기사만" 받는 소비 패턴을 지원한다. 단조 증가 id 라 누락이 없다.

## 3. 데이터 모델

모든 시각은 UTC `YYYY-MM-DDTHH:MM:SSZ` 문자열이다. 같은 형식이라 사전순 비교가 시간순 비교와 같아 인덱스를 그대로 탄다.

| 테이블 | 내용 |
|---|---|
| `articles` | 기사. `url_key`(정규화 URL) UNIQUE, `ts` = 정렬·시간창 기준 시각(`published_at`, 없으면 `collected_at`), `source_key` 는 처음 수집한 소스, `extra_json` 은 소스별 원자료 |
| `article_feeds` | 기사가 실린 모든 피드 (기사–피드 다대다) |
| `article_symbols` | 수집 시 확정된 종목 연결 `(market, symbol, method)` |
| `article_topics` | 주제 태그 |
| `articles_fts` | FTS5(trigram) 전문 검색 인덱스 — 트리거로 `articles` 와 동기화 |
| `sources` | 소스 정적 정보(yaml 반영) + 런타임 상태(ETag, 마지막 성공, 연속 실패, 다음 폴링, 토글) |
| `symbols` | 심볼 사전 (SEC·DART·수동), `rank` 는 원천 목록 순서(SEC 는 대략 시가총액 순) |
| `watchlists` | 클라이언트별 관심종목 — 종목별 소스의 수집 대상 |
| `symbol_fetch_state` | (소스, 종목)별 수집 상태 |
| `fetch_log` | 수집 이력 (7일 보관) |
| `meta` | 주제 규칙 버전, 사전 갱신 시각, 유지보수 날짜 |

`article_symbols.method` 값

| method | 근거 | 정확도 |
|---|---|---|
| `source_tag` | 피드가 명시한 티커(`<category>`, 검색 API 의 관련 티커) | 높음 |
| `dart_code` | DART 공시의 종목코드 | 확정 |
| `edgar_cik` | EDGAR 제출 법인 CIK → 사전 | 확정 |
| `search` | 종목별 검색 소스가 그 종목으로 검색한 결과 | 높음 |
| `ref` | 본문의 명시적 참조 `$NVDA`, `(NASDAQ: NVDA)`, `(005930)` | 높음 |
| `dict` | 사전 회사명·별칭 매칭 | 보수적 규칙 (§4.4) |

## 4. 수집 파이프라인

### 4.1 스케줄

- 전역 소스는 소스마다 `next_poll_at` 을 두고 1초 틱에서 도래한 것만 실행한다(동시 실행 상한 `MAX_CONCURRENT_FETCHES`).
- 다음 주기 = max(기본 주기, 무수집 백오프, 실패 백오프)
  - 기본 주기: `schedule: fixed` 면 `interval_sec`, `market_aware` 면 소스 시장(KR/US/GLOBAL)의 정규장 180초 · 확장 거래 1800초 · 휴장 3600초 (`market_intervals` 로 조정)
  - 무수집 백오프: 연속 5회 10분, 10회 15분, 20회 30분
  - 실패 백오프: 60초부터 두 배씩, 최대 30분
- 조건부 GET(`ETag`/`Last-Modified`)을 보내 304면 파싱을 생략한다.
- 종목별 소스(`per_symbol`)는 관심종목 합집합을 대상으로, 소스마다 한 번에 한 종목씩 `request_gap_sec` 간격으로 순회한다.

### 4.2 정규화

- **텍스트**: HTML 태그 제거 → 엔티티 해제 → 드러난 태그 재제거. 태그명이 영문인 것만 태그로 보므로 제목의 `<종합>` 같은 표기는 남는다. 인라인 서식 태그(`<b>`)는 공백 없이 지워 `<b>삼성전자</b>가` → `삼성전자가`.
- **시각**: 원문 문자열을 RFC 822 → ISO 8601 순으로 파싱한다. 타임존 표기가 없으면 소스의 `naive_tz` 로 해석한다. 문자열 파싱이 실패할 때만 feedparser 의 UTC `struct_time` 을 `calendar.timegm` 으로 변환한다(`time.mktime` 은 로컬 시각으로 해석해 시차만큼 어긋난다).
  수집 시각보다 1시간 넘게 미래인 값은 버리고(NULL), 그 이내면 수집 시각으로 당긴다.
- **날짜만 있는 공시**(DART 접수일): `published_at` 을 비우고 `extra.rcept_dt` 로 보존한다. 날짜 00:00 을 발행 시각으로 두면 장중 공시가 시간창 조회에서 빠진다.
- **URL**: 스킴·호스트 소문자, `www.`/모바일 서브도메인 통일, `utm_*` 등 추적 파라미터와 fragment 제거, 쿼리 정렬.

### 4.3 중복 제거

1. `url_key` 가 같으면 같은 기사다. 기사 행은 하나로 두고 `article_feeds` 에 피드 소속을 추가한다.
2. 뒤에 온 소스가 더 풍부하면 보강한다: 비어 있던 요약, 비어 있던 발행 시각, 추가 종목 태그.
3. 정규화 제목 해시(`title_key`)는 저장만 하고, 조회 시 `dedup=title` 로 교차 소스 동일 기사를 한 건으로 줄인다
   (리다이렉트 URL 을 쓰는 검색 피드처럼 URL 로는 합쳐지지 않는 경우).
4. 보관 기간보다 오래된 항목은 받지 않는다. 받으면 정리 작업이 지우고 다음 수집이 다시 넣어, 증분 커서 소비자에게 같은 기사가 계속 새로 보인다.

### 4.4 태깅

수집 시점에 종목·주제를 붙여 두면 조회는 인덱스 조인으로 끝난다.

- **소스 태그·공시 코드·CIK·검색 대상**: 수집기가 준 구조화 정보를 그대로 쓴다.
- **사전 태깅**(`dict`)은 오탐을 줄이는 쪽으로 보수적이다. 놓친 기사는 조회 시 텍스트 매칭(§5.1)이 보완한다.
  - 자동 수집 이름: 한글 3자 이상 / 영문 한 단어는 4자 이상이면서 일반 영어 단어(`WORDLIST_FILE`)가 아닐 것
  - 영문 이름은 기사에서 각 단어가 대문자로 시작할 때만 인정 (`global industrial` ≠ `Global Industrial`)
  - Title Case 헤드라인(4자 이상 단어의 85% 이상이 대문자 시작)에서는 한 단어 자동 이름을 무시
  - 한 이름이 여러 종목(우선주·OTC 티커)에 걸리면 `rank` 가 가장 높은 종목 하나만
  - 한글 이름 뒤에는 조사만 허용 (`삼성전자에서` ✓ / `삼성전자산업` ✗). 두 글자 이하 이름은 한 글자 조사도 목록에 있어야 함
  - 큐레이션 별칭(`aliases.yaml`, API)은 길이·일반명사 제한을 받지 않되 경계 규칙은 같다
  - `stopnames.txt` 의 이름은 자동 태깅에서 제외
- **주제**: `topics.yaml` 키워드 규칙. 주제가 없는 기사도 저장한다. 규칙 `version` 이 바뀌면 시작 시 보관 중인 전체 기사를 재태깅한다.
- 심볼 사전을 원격에서 갱신하면(기본 7일마다) 보관 중인 기사의 `dict`/`ref` 태그를 다시 계산한다.

## 5. 조회

### 5.1 종목 조회

두 경로의 합집합이다. 결과 항목의 `match` 가 경로를 알려 준다.

- **태그 경로(`tag`)**: `article_symbols` 에서 `(market, symbol)` 로 찾는다. 시장 필터를 적용하지 않는다.
- **텍스트 경로(`text`)**: 종목 코드·회사명·별칭(요청의 `name`/`alias` + 사전)으로 키워드를 만들고,
  FTS5 trigram(3자 이상)·LIKE(3자 미만)로 후보를 추린 뒤 `matching.py` 규칙으로 정밀 검증한다.
  - 영문 키워드는 영숫자 경계, 한글 키워드는 조사 규칙
  - 영어 단어와 같은 미국 티커(`ALL`·`ON`·`IT`)는 대문자 표기만 인정. 단, 회사명 첫 단어가 티커와 같고
    회사가 그 단어를 대문자 전용으로 쓰지 않으면(Meta·Arm) 대소문자 무시
  - 법인 접미사를 뗀 상호도 키워드에 포함 (`NVIDIA Corporation` → `NVIDIA`)
  - 기본으로 같은 시장 소스로 제한(`market_filter`)
- **공시**: 본문이 메타데이터라 텍스트 근거로 약하다. `filings=auto`(기본)면 태그로 특정된 공시만 포함한다.

### 5.2 공통 필터와 정렬

시간(`hours`/`since`/`until`, 기준 `ts` 또는 `collected_at`), 피드(`sources`/`exclude_sources` — 제외는 "그 피드들에만 실린 기사"),
카테고리, 언어, 종류(뉴스/공시), 요약 유무, 주제(any/all), 전문 검색. 정렬은 `ts` 내림차순, `since_id` 를 주면 id 오름차순.

### 5.3 증분 커서

`since_id` 를 주면 `id > since_id` 를 id 오름차순으로 돌려주고 `next_since_id` 를 준다. 새 기사가 없으면 받은 커서를 그대로 돌려준다.
과거 기사를 건너뛰려면 처음에 `limit=1` 조회의 id 를 커서로 저장한다.

## 6. 운영

- **상태**: `GET /health` — `ok` | `degraded`(스케줄러 30초 무응답, 또는 활성 전역 소스가 모두 2회 이상 연속 실패).
  상태가 바뀌면 경보(텔레그램 설정 시)를 보낸다. `sources_stale` 은 6시간 넘게 성공이 없는 소스.
- **소스 상태**: `GET /v1/sources` — 소스별 마지막 성공·연속 실패·오류·24시간 수집량. `fetch_log` 7일치로 장애 구간을 추적한다.
- **일일 유지보수**(`MAINTENANCE_HOUR`, 기본 03시 `LOCAL_TZ`): 보관 기간 정리(5,000건 배치로 쓰기 락을 짧게) → 수집 이력 정리 →
  (일요일) `incremental_vacuum`·FTS `optimize` → gzip 백업(`BACKUP_KEEP` 세대) → 심볼 사전 갱신(주기 도래 시).
- **로그**: `data/logs/server.log` (20MB 회전, 5개), 프로세스 표준 출력은 `data/logs/stdout.log`.
- **운영 콘솔**(`GET /`): 소스 상태·수집 이력, 조회 테스터(매칭 경로·검색 키워드 표시), 수집량·용량 예측, 태깅 미리보기·별칭 편집.
  API 를 그대로 쓰는 정적 페이지 하나라 빌드 단계가 없다. 외부 피드 텍스트를 DOM API 로만 렌더링한다(`innerHTML` 미사용).
- **접근 범위**: 기본 `127.0.0.1`. LAN 공개(`SERVER_HOST=0.0.0.0`) 시 `API_TOKEN` 으로 쓰기 요청만 보호하고 조회는 열어 둔다.
  공유 토큰 하나라 신뢰할 수 있는 내부망 전제다.

## 7. 확장

| 하고 싶은 것 | 방법 |
|---|---|
| RSS 피드 추가 | `sources.yaml` 에 항목 추가 후 재시작 |
| 새 종류의 소스 | `collectors/` 에 `Collector` 구현(`fetch` 또는 `fetch_symbol`) → `collectors/__init__.py` 에 등록 |
| 종목별 검색 피드 | `kind: rss_search` + `url` 의 `{query}` 자리표시자 + `per_symbol: true` |
| 주제 추가·수정 | `topics.yaml` 편집 후 `version` 증가 → 재시작 시 재태깅 |
| 종목 별칭 | `aliases.yaml` 또는 `PUT /v1/symbols/{market}/{symbol}/aliases` |
| 오탐 회사명 제외 | `stopnames.txt` |
| 새 시장 | `markets.py` 의 별칭·장 시간과 `MARKETS` 에 추가 |

향후 선택지: 본문 추출(별도 `article_bodies` 테이블), LLM 보강 결과 공유(`article_enrichments`), SSE 푸시(`/v1/stream`).
API 는 `/v1` 에서 필드 추가만 하위 호환으로 허용하고, 파괴적 변경은 `/v2` 로 낸다.

## 8. 저장 용량과 보관 기간

### 8.1 측정

실제로 수집한 기사 555건(제목 평균 49자, 요약 평균 99자, 피드·종목·주제 태그 포함)을 복제해 1년치 규모의
DB(110만 건, 365일에 고르게 분산)를 만들어 측정했다.

| 항목 | 크기 |
|---|---|
| FTS5 trigram 인덱스 | 710 MB |
| articles 테이블 | 633 MB |
| articles 인덱스 | 260 MB |
| 피드·종목·주제 테이블과 인덱스 | 139 MB |
| **합계** | **1.83 GB (기사당 약 1.66 KB)** |

같은 DB에서 조회 지연(웜 캐시):

| 조회 | 지연 |
|---|---|
| 종목(한글) 24시간 / 30일 / 전체 1년 | 23 / 34 / 49 ms |
| 종목(미국) 30일 | 11 ms |
| 주제 72시간 | 92 ms |
| 시장별 24시간 250건 | 3 ms |
| 전문 검색 30일 | 38 ms |
| 증분 커서 500건 | 4 ms |
| 주제 통계 90일 | 766 ms |

gzip 압축률은 실제 기사 DB 기준 26~36% (복제 데이터는 반복이 많아 과대평가되므로 쓰지 않았다).

### 8.2 유입량 가정

기본 소스 구성에서 하루 신규 기사는 금융 RSS 약 1,000건, 일반 뉴스 수백 건, 공시(영업일) 약 1,000건 이상,
미국 8-K 약 160건, 종목별 소스는 관심종목 수에 비례한다. 넉넉히 **하루 3,000건**으로 잡으면 1년 110만 건으로
위 측정 규모와 같다. 실제 유입량은 `GET /v1/stats` 의 `intake.avg_per_day` 로 확인한다.

### 8.3 결정

- 기본 보관 **365일** (`DEFAULT_RETENTION_DAYS`), 일반 카테고리(사회·세계·연예·스포츠) 90일, EDGAR 8-K 180일.
- 1년 정상 상태 추정: DB 약 1.8 GB + gzip 백업 3세대 약 2 GB(1세대 약 0.65 GB) + 백업 중 임시 파일 1.8 GB = **최대 약 5.6 GB**.
- 1년 창에서도 조회 지연이 대부분 100 ms 이내라, 보관 기간을 늘려도 조회 성능 문제는 없다.
- 운영 중에는 `/v1/stats` 의 `projection`(콘솔의 수집량·용량 탭)으로 실제 유입 기준 예상 용량을 확인한다.
- 디스크가 부족해지면 순서대로: `BACKUP_KEEP` 축소 → 일반 카테고리 보관 단축 → `DEFAULT_RETENTION_DAYS` 축소.
  보관 기간을 줄이면 다음 유지보수 때 삭제되고, 빈 페이지는 주간 `incremental_vacuum` 으로 반환된다.

## 9. 알려진 한계

- 장 운영 시간 판정은 공휴일을 반영하지 않는다(폴링 주기 결정용이라 영향이 작다).
- 조건부 GET 을 지원하지 않는 피드는 매번 전체를 받는다.
- 피드당 한 번에 `max_entries` 건만 처리하므로, 폴링 간격 동안 그보다 많이 발행하는 피드는 일부를 놓칠 수 있다(`fetch_log.n_items` 가 계속 상한이면 간격이나 상한을 조정).
- 사전 태깅은 영문 헤드라인의 Title Case 여부를 휴리스틱으로 판정한다.
- 종목별 검색 소스는 해당 서비스의 이용 약관 범위에서만 사용한다(Google 뉴스 검색 RSS 는 기본 비활성).
